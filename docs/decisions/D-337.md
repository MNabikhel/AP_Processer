- **D-337** · **A release's update test in one command, `scripts/release_proof.py --from OLD --to NEW`: OLD unzipped and
  used in a home of its own, then "Update now?" answered in its window, a pseudo-terminal; GitHub answers the
  launcher when NEW is its newest release, else a stand-in on 127.0.0.1 that a sitecustomize on PYTHONPATH puts in
  front of the launcher's own releases module** (D-243, D-247, D-94).
  - **Why:** the update test done by hand for each release (efbd375, 0a749b3: a dozen tools, about two hours) found
    what no test of the parts does, and every merge to main is a release the owner's launcher offers. Only the
    newest release is offered by GitHub: an older pair of tags, or a ZIP of a pull request, can't be tested through
    it, and nothing of the launcher may change for a test.
  - **How:** each build a tag (its ZIP and SHA256SUMS through scripts/releases.py's own requests, only with
    AP_ALLOW_INTERNET=1) or a ZIP laid out as a release's. OLD's APProcessor.command runs as a person's double-click
    (HOME a folder of its own, no AP_ setting, its first setup downloading what it needs as D-94 has it); the first
    sign-in, the demo, the made-up company with two invoices approved and its workbook loaded reuse
    scripts/ci/first_day.py and the bench's browser. Its second start answers the question; the stand-in's
    sitecustomize sets only `API`, `HOSTS` and `SCHEME` of the module named `releases`, as it is imported. Then each
    table of both data folders is compared row by row with its copy from before: what an update always changes is
    named (`why_changed`: files_moved, the re-check, the search index's pages, the reports' kept answers, the
    proof's own sign-in), anything else fails; also the Version line, the approved invoices and their PDFs, the
    doctor, the workbook check, the notes folder's README.txt and every log line that looks like an error. Exit 0
    only when all pass. 0a749b3 to be6964b, asked of GitHub: 21 of 21, the update about 100 s from the answer.
  - *Not chosen:* an address for the release check in an environment variable of the launcher (every person's
    launcher would carry a way to point it elsewhere); a proxy before api.github.com with a certificate of its own
    (pip's downloads would go through it too); the newer ZIP unzipped by hand (CI's windows-github-zip job: not the
    question the pilot tester answers); Windows (no pseudo-terminal in Python's standard library: it refuses).
