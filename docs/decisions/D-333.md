- **D-333** · **A function-level test map: `tests/test_map.py` writes `tests/test_map.json.gz`, each function of the
  app with the test files that ran it, from coverage recorded with each test's file as its context** (D-233, D-329).
  - **Why:** picking tests by file name and import misses the tests of a function used far from its module
    (`taxmath.invoice_taxes`, `Store.final_approve`), while the import graph at distance 1 picks 70 to 76% of the
    test files (the weekend's audit): the whole suite in disguise. A map of which files ran which function picks few.
  - **How:** `python -m tests.test_map record -- <pytest args>` runs pytest under coverage with the module as a
    plugin that switches coverage's context to the running test's file (setup and teardown too), then combines the
    data and writes the map: keys `ap_coder/<path>::func` or `::Class.func` (a nested function counts for the outer
    one), each with indices into the sorted test files, gzipped JSON with no time in it, so the same run gives the
    same bytes. `load()`, `tests_for(keys)` (the files, and whether each key is in the map: a function no test ran
    is not, and is picked another way), `keys_for_lines` (a change's lines as keys) and `stale` (keys the code no
    longer has) are what check.py reads. coverage is a new extra, `testmap`, never `dev`: the offline bundle's
    default extras carry `dev`, and reading the map needs nothing. Measured on tests/coding and tests/erp: 1,858
    tests in 603 s under coverage, 3,830 functions and 79 test files, 36,875 bytes; built again, the same bytes.
  - *Not chosen:* pytest-cov's `--cov-context=test` (a second package for the same contexts; its node ids read the
    same); coverage's `dynamic_context = test_function` (it leaves fixtures' work out); one context a test (a
    database many times bigger for no better pick: the map keeps files).
