- **D-336** · **In the tests a new database is a copy of one made the real way as the run starts** (D-329, D-333).
  - **Why:** a new Store makes the schema and runs every migration (35-40 ms), and the tests make about one for every
    two tests; a copy and its start take 8 ms. On one core, the default run's test time: coding 70 to 58 s, core 112
    to 94 s, web 484 to 448 s, the other folders 481 to 453 s (about 10% in all); each of its 7,846 tests with the
    same outcome as before, and the slow tests of coding, core and web too.
  - **How:** `tests/conftest.py`: at the session's start one Store is made the real way in a temporary folder
    (removed at the end), then `StoreCore.__init__` is `_new_store`: on a path where no database, journal or
    write-ahead log is yet, SQLite's backup of it goes to a file beside it, gets a summary_id and a rule_use_since of
    its own as a new database writes them, and is put at the path with `os.link` (a database made there meanwhile is
    never overwritten; any failure leaves the real way to make it); then the real `__init__` runs, as on any database
    up to date. The app, the processes a test starts and a forked child (another pid) make theirs the real way, and
    so does a test marked `real_new_database` (or code inside `with real_new_databases():`).
    `tests/meta/test_new_databases.py`: a copy has the sqlite_master, rows, settings (its summary_id apart) and
    pragmas of a real new database. The numbered migrations now run in the tests of older databases, not in every
    test making a new one (the test map).
  - *Not chosen:* the copy written straight at the path (a process making the database there meanwhile would lose
    its own); one transaction around the migrations (no gain: 35.0 against 37.1 ms); a copy for the `store` fixture
    alone (most new databases are made by `Store(...)` in the tests themselves).
