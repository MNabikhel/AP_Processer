- **D-339** · **The tests' times and the test map are measured every night by CI and put on a data branch of their own,
  `test-times`, that nothing runs on; `python -m tests.times pull` brings them into a checkout, to commit with a pull
  request; Windows' parts are split by Windows' own times (`tests/test_times_windows.json`)** (D-233, D-260, D-333).
  - **Why:** the times were refreshed by hand from a whole local run and went stale (7 test files with none; on
    Windows the four parts of one cell took 12 to 19 minutes, split by Ubuntu's times: Windows reads the scans and
    takes two to three times as long, unevenly; by its own, about 15.5 each), and the map was recorded once. Every
    green run of a merge to main is a release the pilot tester is offered (builds.yml), so a refresh must never go
    to main by itself; a bot's pull request each night is one more thing to look after, and a new secret one more to
    guard.
  - **How:** ci.yml's nightly (and a run by hand) on main only: test-map records the map in four parts side by
    side (`--shard K/4` under coverage), test-times then works out each file's time from the tests parts' kept
    `--junitxml` reports (`python -m tests.times ci`: the mean of the Pythons that ran the whole suite, Ubuntu's and
    Windows'; the fast tier's cells have no slow test's time), joins the map once all four parts made theirs
    (`python -m tests.test_map merge`; else the last one stays), and force-pushes one commit of those files alone,
    with made.json (the commit, run and date), to refs/heads/test-times with the run's own token (`contents: write`,
    that job alone). A push by that token starts no workflow, and the branch holds no workflow file; builds.yml
    releases a merge's run only. Both jobs are `continue-on-error`: they never turn the nightly red. `pull` (only
    with AP_ALLOW_INTERNET=1, from raw.githubusercontent.com; or `--from file://...`) puts the times over the
    checkout's (a test file added since keeps its own, one gone leaves) and the map as it is; it says the date, so
    data gone stale shows. On win32, `_shard` reads the Windows times over Ubuntu's. Refreshed now from main's run
    of be6964b: Ubuntu 403 files, 34.3 minutes (15.4 without the slow tests); Windows 402, 62.0.
  - *Not chosen:* the nightly pushing to main (a release offered for data); a pull request opened each night (one
    to merge or close every day); a commit to main by hand from the artifacts (the stale times this replaces); a
    separate workflow on workflow_run (write access outside CI's jobs, run only after Mac jobs finish); a repository
    secret or app token (the run's own token reaches the branch); the map recorded in one job (about an hour, over
    CI's one-hour limit a job).
