- **D-159** · **What a web worker keeps between requests, and how it knows it still holds** (phase 2 part 2's CPU: `docs/archive/scale-2026-11/cpu.md` items 1-3, 5, 7 and 10).
  - **Why:** the check and the invoice page redid, on every request, work whose answer changes a few times a day:
    - the vendor master turned into a dict of 20,000 vendors, twice;
    - the held vendors' approved numbers, twice;
    - the GL suggestions' index of 50,000 lessons, again for each vendor in turn;
    - the queue's checks and list.
    - Together that was 82% of the CPU asked at 100 people.
  - **The rule:** a kept answer holds only while a stamp, read from the database in the same request and before the work, says nothing it depends on changed. It does not matter which process changed it (another worker, the background process, plain SQL). Never a timer, never "this process wrote it".
    - `Store.summary_memo` gives the stamp: the database's id (`summary_id`, new after a restore or a summary rebuild), a summary topic's generation, an event count.
    - New: `changes`, a count kept by triggers; `asked`, what the answer is for (a list's invoices, the vendors asked).
  - **Counts kept by triggers** (in `summary.SUMMARY_TRIGGERS`, made at every start, so a backup with them restores):
    - `changes/vendors`: every change to the vendor list (a 20,000-vendor import: 0.30 s against 0.24-0.42 s).
    - `changes/approved`: an invoice approved or no longer approved, or its vendor or coding changed while approved. An export changes nothing.
  - **Two summary topics:**
    - `queue`: what the queue reads of an invoice in review. One the summary could not work out counts at each write.
    - `listed`: the queue's invoices as `list_invoices` lists them, confidence included.
  - **What is kept** (its stamp; what it holds at 100k):
    - **The vendor master's ERP IDs** (`vendor_ids`): `changes/vendors`; 6.5 MB.
    - **The master's GST/HST numbers** (`master_by_tax_number`, for an invoice not found by name): `changes/vendors`; 7 MB. Only the vendors found are read.
    - **The held vendors' approved numbers** (`approved_numbers`): `changes/approved` and the vendors asked; 0.2 MB. When read, it seeks the vendors' index: 180 → 20 ms.
    - **The queue's checks** (`bulk.queue_checks`): `queue`, the checks stamp, laptop or server, the invoices asked; 18 MB. Fewer than 50 invoices are worked out each time.
    - **The queue's lists** (`list_invoices` of review, parked, pending): `listed`; 2.8 MB each. Each caller gets copies.
    - **The GL suggestions' index:**
      - the shared memory's index is built once per change of the lessons (D-154's stamps);
      - a vendor's older lessons past the cap (`learning_rows` returns `WithPast`) extend it (`suggest._with_past`, `Index.extended`): what a whole build gives, in 6-13 ms instead of 0.2-0.75 s, 0.4 MB each;
      - kept for 32 vendors and 60,000 of their lessons (about 80 MB) per process, the latest always; the store keeps those lessons the same way (`_PAST_MEMORY`, 2 vendors before).
    - **A line's suggestions** (`_Memory.said`): with the memory and the reference data they came from; 1,024 per memory, about 1 KB each. Callers get copies.
  - **Measured** (100k, one worker, CPU, four vendors in turn):
    - the check 1,244 → 96 ms;
    - the invoice page 1,811 → 544 ms; its vendor list is two thirds of what is left;
    - `/review` 247 → 61 ms; its tabs 212-449 → 42-190 ms;
    - the page's Previous and Next 26 → 1 ms.
  - **Not done:**
    - a vendor's invoices (`vendor_invoices`), 70-80 ms per check for the biggest;
    - the vendor list in the page;
    - the memory's whole index once per worker after each approval;
    - the queue's answers refreshed row by row after a park.
