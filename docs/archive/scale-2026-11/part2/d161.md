- **D-161** · **Static files from memory at kept addresses, no compression, polls that wait, and a busy web worker that hands its connections back** (B-1720; the phase 2 load run's 16-57 s static waits and its 0.34-1.0 cores workers).
  - **Static files from memory:** `core.read_static` reads the styles, scripts, fonts and logo once when AP Coder starts. `app.StaticFromMemory` answers a GET or HEAD of one on the event loop: after the Host check, with the security headers and the access log, before the session, the errors page and the backup check.
    - The same status, headers and 304s as Starlette's `StaticFiles` (its own ETag and Last-Modified, so a browser's copy stays current across the change), laptop and server; a test compares every file, both modes. `StaticFiles` still answers what memory doesn't: a Range, a POST, a file that isn't there.
    - Why: a static file costs 1-2.7 ms, but `StaticFiles` reads it on one of the worker's 4 threads (D-153), behind 1-2 s pages. Server CPU through uvicorn: a 304 0.90 → 0.46 ms, app.css 1.48 → 0.41 ms, the 373 KB icon font 2.72 → 0.52 ms; no thread.
    - A file edited while AP Coder runs is answered as it was at the start (a developer restarts `serve`).
  - **Kept addresses:** the pages link each file at `/static/<build>/...` (`/fonts/<build>/...`, `/assets/<build>/...`) through `core.static_url`, with `Cache-Control: public, max-age=31536000, immutable`; the kept stylesheet names the fonts at theirs.
    - The build is a hash of the files' contents, not the commit: a checkout's commit doesn't change with an edit not yet committed (the edited script would be kept a year), and an update that changes no file keeps everyone's copies.
    - Another build's address (a page drawn before an update) answers the file as it is now, `no-cache`. The plain addresses answer as before. Pages stay `no-store`.
    - Every template uses `static_url` (a test fails on a plain address: a page script loaded at its plain address would be a second app.js module).
  - **Measured** (bench load on a 3,000-invoice seed, 60 people, think 4 s, 2 web workers, 180 s; the 4 cores shared with other agents), before → from memory → kept addresses too:
    - requests 22,834 → 26,344 → 6,045 (27,506 more from the browsers' caches);
    - `/static` p95 1.82 s → 130 ms → 67 ms; `/fonts` and `/assets` p95 1.79 and 1.96 s → 25 and 52 ms;
    - pages p50 3.25 s → 466 ms → 269 ms, p95 49.4 s → 6.10 s → 1.67 s;
    - actions p95 50.8 s → 12.3 s → 2.05 s; requests over 30 s 745 → 0 → 0.
  - **No compression** (laptop and server).
    - gzip's CPU per MB of AP Coder's HTML and JSON (100k database): level 1 4.4-6.6 ms, level 4 7.3-11.7, level 6 14-18, level 9 (Starlette's `GZipMiddleware` default) 60-75.
    - On the office's gigabit network the old 3.6 MB invoice page took about 29 ms, which cost the server nothing; level 1 would cost 4-5 core-s a minute at 100 people (3% of the 4-core budget, cpu.md) and save no time anyone sees. The page is now 0.3 MB (D-160).
    - Where it matters (a VPN at 20 Mb/s), IIS in front compresses `text/html` and `application/json` only, at its lowest level (SERVER.md). Never a stream or file (CSV, xlsx, PDF, PNG, ZIP). Static files are not compressed either: each browser fetches them once per build. The vendor list (D-160) is sent gzipped from what the worker keeps, at no CPU per request.
  - **Polls** (`app.js` `poll`, used by `pollJob` and the review screen's reading):
    - Nothing while the tab is hidden; a look at once when it is back.
    - After an answer the same as the last (or none), half as long again, up to three times the pace (a job's at least 5 s); a change starts again at the pace.
    - A look answered by the login (a 401, or a GET sent on to /login) stops it (B-1720); the job pages then go to the login and come back after it.
    - `watchJob` asks `/jobs/<name>?only=done,note`: the state, done and note, not the job's 500 lines.
    - Every fetch has a deadline (`fetchWithin`, AbortController): a look 30 s (the vendor list too), an action (`post`) and the setup report 5 minutes; past it, the existing "didn't answer" wording.
  - **The workers' balance:** a busy worker hands its connections back (`server.HandBack`): while requests wait for one of its threads, its answers say `Connection: close`. `KEEP_ALIVE_SECONDS` stays 75.
    - How a connection finds a worker: the workers listen on one socket, and the first to `accept()` takes it, on Linux (epoll; no `SO_REUSEPORT`) and on Windows (uvicorn's supervisor shares the listening socket, B-1711, and each worker runs the selector loop). A free worker's loop usually wins it.
    - What kept people on a busy worker is the browser keeping its connections (minutes) and the server 75 s. The harness's people closed theirs after 5 s unused (httpx's default), which hid it: `bench load --keep-alive 300` keeps them as a browser does (the default stays 5, so earlier runs compare).
    - Measured with people keeping connections 300 s: 50 people, think 10 s, 4 workers: one worker did 54% of the work. Saturated (60 people, think 4 s, 2 workers), three pairs run back to back: pages p95 5.2 / 24.0 / 33.3 s with 75 s alone, 4.1 / 19.6 / 16.6 s with HandBack; requests over 30 s 0 / 147 / 343 against 0 / 74 / 9.
    - A shorter keep-alive was refused: at 5 s, 12 requests got no answer in the saturated run (B-1295's race: an idle connection closed as the browser sent on it).
    - `Connection: close` comes in the answer: the browser opens a new connection for its next request, nothing is lost, and IIS ARR in front does the same. A new HTTPS connection costs the worker that takes it 1.2 ms (0.4 ms resumed).
  - **Not done:** the import's poll still sends its lines (up to 500, 57 KB; process.js shows them all); an upload (XHR) has no deadline (it may take minutes); a poll without a session still draws the login page once before it stops (`identity.py`); the access log writes on the event loop (`security.py`).
