# Decisions

The significant choices behind AP Coder, one line each: the choice, why, and where it is written or enforced.
Add the next number when a change makes a new choice (and say so in the pull request); never renumber. A choice
that is reversed keeps its line, marked "replaced by D-NN".

## Running offline

- **D-01** · Fully offline at run time; the one opt-in to the internet is `AP_ALLOW_INTERNET=1` (developers, the bundle builder). Why: invoices and company data must never leave the laptop. (`ap_coder/ops/offline.py` `internet_allowed`, README "Run it by hand")
- **D-02** · Azure (Document Intelligence check, Azure OpenAI) is optional, off by default, and never needed to install or start; its packages are an extra. Why: the pilot runs with no cloud account; Azure is a second opinion, not a dependency. (`pyproject.toml` `azure` extra, `ap_coder/ai/azure_check.py`, `tests/test_azure_optional.py`)
- **D-03** · The offline proof: tests run AP Coder under a socket guard that refuses and records any connection not to this computer (127.0.0.0/8, ::1, localhost), and CI installs the bundle with every proxy pointed at a closed port. Why: "offline" must be shown, not promised. (`tests/offline_guard.py`, `tests/test_offline_guard.py`, `.github/workflows/ci.yml`)
- **D-04** · LM Studio is reached only on this computer or the office network; an internet address is refused however it is written, unless `AP_ALLOW_INTERNET=1`. Why: a model server URL is the easiest way for data to leave. (`ap_coder/ai/local_llm.py` `refused_address`, `ap_coder/core/config.py` `_on_this_network`, docs/BUGS.md B-39)
- **D-05** · An offline bundle (code, `wheelhouse/`, `models/`, `bundle_manifest.json`) installed with `pip --no-index`. Why: the pilot laptop has no internet; one ZIP must install everything. (`scripts/build_offline_bundle.py`, `scripts/launch.py`)
- **D-06** · No CDN: fonts, icons, styles, scripts and charts (hand-made SVG) all ship in the package. Why: a page that loads anything from the internet would not work offline; the offline proof reports any such address. (`ap_coder/web/__init__.py`, `ap_coder/web/charts.py`, `tests/offline_flow.py`)
- **D-07** · RapidOCR stays on 3.4.x, and its PP-OCRv5 models are copied from the bundle, never downloaded by RapidOCR. Why: the capture confidence table is fitted on its reads; later 3.x releases change the model list. (`pyproject.toml` `ocr` extra, `scripts/fetch_models.py`, `ap_coder/ops/offline.py`)

## Data and install

- **D-08** · One data folder outside the code (default `~/APCoder`, recorded in `~/.ap_coder/settings.json`) for the database, invoices, outputs and `.env`. Why: unzipping a new version must never lose or duplicate data. (`ap_coder/core/paths.py`, `scripts/upgrade.py` `settle_data_folder`)
- **D-09** · SQLite, one file in the data folder; a backup once a day when the dashboard starts (newest 14 kept), an optional second backup folder; a newer database is refused and an older one backed up before migrating. Why: a single laptop needs no server, and an update must never risk the data. (`ap_coder/core/store.py` `auto_backup`, `copy_backup`, `_before_migrating`; `tests/test_update_database.py`, docs/WHATS_NEW.md)
- **D-10** · No company data in the repo: `private/` and `.env` are git-ignored, and so are every `.xlsx` and the PDFs and TIFFs at the top of the repo. Why: the repo is shared; invoices are confidential. (`.gitignore`, `private/README.md`)
- **D-11** · Never two versions on one database: a start finds a running AP Coder (`/healthz`), opens it if it is the same version and folder (or newer), stops an older one or one from another folder (`POST /shutdown` with a token). Why: older code must never write to a newer database. (`scripts/running.py`, `scripts/launch.py`, `ap_coder/web/app.py`)
- **D-12** · One button per computer (`APProcessor.bat`, `APProcessor.command`) that sets up only what is missing; the installer is the same setup with questions. Why: the pilot tester double-clicks one file; the older install and start scripts are gone and an update removes them. (`scripts/launch.py`, `scripts/install.py`, `scripts/upgrade.py` `prune_stale`, docs/WHATS_NEW.md)
- **D-13** · Two people approving share one AP Coder on one PC, the database on a local disk, not a network share. Why: an open SQLite database can be damaged on a network share or a synced folder; a shared server version is a Phase 2 item. (docs/WHATS_NEW.md "Second approval", docs/GETTING_STARTED.md "Two people approving", docs/PILOT.md)

## Dashboard

- **D-14** · The dashboard is a local FastAPI app (uvicorn) on 127.0.0.1, replacing the Streamlit dashboard. Why: faster pages, an address per page, nothing from the internet, and hosted the same way as CloseDesk. (`pyproject.toml`, `ap_coder/web/`, docs/WHATS_NEW.md "the dashboard is a local web app")
- **D-15** · Only this computer's host names are served; writes need the `X-AP-Coder: 1` header and a same-origin request, and every redirect stays local. Why: another web page in the same browser must not drive AP Coder. (`ap_coder/web/security.py` `LocalOnly`, docs/BUGS.md N-20, N-21)
- **D-34** · Shared on the office network (`AP_DASHBOARD_ADDRESS=0.0.0.0`), each browser on another computer gives its name once on a "Who are you?" page; the name is kept in a cookie the server signs (HMAC-SHA256) with a secret made at each start, and stands for that person: approvals and events name them, every event records their address (`detail["address"]`, also from a thread pool the request started), their computer's address stands for a login (so a second approval from the first approver's computer is refused, whatever name it gives), and their unsaved review edits are their own. This computer's browser is never asked. No passwords: the office network and the second-approval rule are the controls; a restart asks everyone again. Why: on the network every action was recorded as the server's user, so a colleague could not give the second approval (W2-02, docs/BUGS.md N-57). (`ap_coder/web/identity.py`, `ap_coder/web/pages/who.py`)
- **D-48** · After Approve, Park or Reject the review screen opens the invoice that followed this one when its screen was drawn (`next_id`), while it is still waiting; the queue's order is not frozen otherwise. And *Your province* is a getting-started row (recommended) but not one of the steps counted in the ring. Why: the queue is ordered by a confidence that the open invoice's own edits refresh (so the queue shows what the screen shows), and the next invoice taken from its new place skipped the ones between (B-426); the province makes the sales tax check work on invoices without a ship-to, but AP Coder works without it, and counting it would change every count the first-launch pages and their tests agree on (B-437). (`ap_coder/web/pages/invoice.py` `next_url`, `ap_coder/web/pages/process.py` `province_step`)
- **D-49** · Over the first 50 reviewed lines the review queue and Learning show the coding accuracy with a plain note ("GL suggestions improve as you approve", plus "; with the AI model on they start sooner" without a chat model) instead of the red distance to the 90% target; after them the distance shows, with the note's first half while there is no chat model (B-447); D-39's definition is unchanged. And with LM Studio itself not running, the review screen says so once, in the banner, and leaves out the OvisOCR2 and AI reviewer notes that repeated it. Why: on the pilot's first day both read as alarms about something nobody could change, and the three notes pushed the invoice below the fold on a 1366 x 768 laptop (docs/BUGS.md B-442, B-444). (`ap_coder/web/core.py` `accuracy_note`, `ap_coder/web/pages/invoice.py` `lm_studio_off`)
- **D-52** · What the pilot shows (owner's decision, before testing): the menu shows the seven pages a tester uses every day (Review queue, Import invoices, Invoice directory, Exports, GL accounts & tax, and Settings and Help pinned above the footer); the other nine fold under **More**, which opens by itself on one of its pages and otherwise stays as that browser left it (`localStorage`). LM Studio runs for the pilot: it is step 0 of the Quick start and the first row of the welcome checklist, with **Check again**. Exports are Excel or CSV: the JD Edwards E1 tab and export format show only once Settings → About's *Show JD Edwards settings* is on (a database setting; nothing removed, `/settings/jde` still opens and says so). Developer tools (Learning → Readers, the training data export, the developer changelog, the Azure check's page offline) show with *Show developer tools* or `AP_DEVELOPER_TOOLS=1`. Settings opens on Review. Why: the audit found the menu longer than a laptop screen, and pages a tester never needs (JD Edwards, readers' scorecards) in the way of the ones they do. (`ap_coder/web/pages/__init__.py` `more`, `ap_coder/web/core.py` `jde_shown`, `developer_tools`; docs/BUGS.md B-502 to B-525)
- **D-56** · The long choices are picked from a searchable list (`static/js/picker.js`, plain JavaScript, loaded on every page): a line's GL account and cost center, Split a line and Apply to all, the fixed rules on GL accounts & tax, the vendor on Vendor statements; the review screen's vendor and currency take it in free-text mode (what is typed is the value; the vendor list replaces the `<datalist>`). It enhances the native `<select>`, which stays in the form, hidden under the box, with its name: its value is what is posted, so the server, `LINE_INPUTS` and the checks are unchanged, and a pick fires the select's own `input` and `change`. Every word typed must be in the code or the name (accents and case aside); while nothing is typed a line's account list starts with *Used for this vendor* (the accounts this vendor's approved lines went to, most used first, from the decided lessons only: `invoice_view.vendor_accounts`) and *Suggested* (the line's suggestions card). The review screen prints the GL accounts and cost centers once, as JSON (`#gl-options`, `#cc-options`); a line's select holds only its own choice and *Needs an account*, so 20 lines no longer carry the chart of accounts 20 times. Without JavaScript a line's select therefore offers only its choice and *Needs an account*: a progressive enhancement we accept, the review screen needing JavaScript for its checks anyway. Short selects (province, tax, sort orders, the words chooser after a drag) stay native. The list opens on typing, a click, Alt+↓, F4 or Enter (Space on a box without a choice), never on the focus alone: tabbing through a grid of 20 lines stays quiet, and the text shown is selected so typing replaces it. Tab and Ctrl/⌘+Enter pick only the choice highlighted from the keyboard once something was typed, never the row the mouse rests on (Enter and a click do pick that one); Ctrl/⌘+Enter then goes on to approve with it (B-590, B-595). The vendor list ends with *Not in the vendor list: add as a new vendor…* while the name typed is not in it (B-597), and *Used for this vendor* follows the vendor field through each check of the edits (B-596). The list follows its box as the page scrolls and closes once the box is out of sight (B-593). Why: the pilot tester found the dropdowns lacking: a native select only jumps by first letters, and 300 accounts × 20 lines were about 6,000 options in one page. (`ap_coder/web/static/js/picker.js`, `ap_coder/web/static/picker.css`, `ap_coder/web/templates/_invoice_lines.html` `few`, docs/BUGS.md B-563, B-564)
- **D-57** · The review screen's page viewer works like a document viewer, offline and in plain JavaScript (no PDF.js): the page is a PNG drawn on the server, zoomed from 50% to 400% (Fit width and Fit page follow the window; the zoom is remembered in the same browser setting as before, so "100" and "150" saved by older versions still load), with the Hand to drag it and Rotate to turn it a quarter turn on screen only (per page of the open invoice, never saved or sent). The page and its boxes are one sheet turned with a CSS transform, so the boxes and the words to teach from turn with it, and the pointer is turned back to page fractions. Zoomed in, the picture is asked for again at `?scale=2` or `3` (240 or 360 dpi, capped at 4,800 and 6,000 px; a scan, a picture or a PDF page that is one scanned picture, is never drawn beyond its own resolution, B-594) once the screen shows more than 1.25 or 2.5 screen pixels per picture pixel, loaded aside and swapped in, and kept when zooming out; the server keeps the pictures drawn up to 96 MB in all, the least recently used going first. The tools above the page take one row (zoom, fit, the Hand, Rotate, *Next to check*, then the pages; "Page" folds to "1 of 2" beside the form), the colour key and *To check only* sit on the *Fields* line (the counts in words stay for a screen reader), and the teach bar puts its buttons on its title's line: at 1366 x 768 the page shows 345 px instead of 305 before the screen scrolls, 514 instead of 474 once the card is stuck. A tag in the page's corner says when the Hand is on (*Hand: drag to move · H to turn off*) and when the page is shown turned (*Turned 90°: view only, nothing is saved*); it never takes the pointer. Space holds the Hand only with the focus on the page, or nowhere with the pointer over it, and Page Up / Page Down turn the pages only from the Document card: the form's boxes and buttons and the screen's scrolling keep their keys (B-591, B-592). Why: the pilot tester found zoom lacking (B-580); a vector renderer in the browser would need PDF.js (a download) and could not show scans and photos the same way, while PNGs at three scales cost one request per page zoomed. (`ap_coder/web/static/js/invoice_viewer.js`, `ap_coder/web/document.py` `page_png`, `clean_scale`)
- **D-59** · The review screen's line grid is the tighter one (B-479: the captions *GL account*, *Amount*, *Qty*, *Unit price* on the first line only, one-line description boxes, the taxes on one line) from 4 lines, no longer from 11: a line takes about 105 px instead of 150, so at 1366 x 768 three lines show beside the page where two did. Up to 3 lines every line keeps its captions: they all fit anyway, and a short invoice is where a first-time tester reads them. The rows and the Tab order are unchanged. Why: the reviewer of the pilot build found only about two lines in view, the grid scrolling away from the page being checked. (`ap_coder/web/templates/invoice.html` `compact`, `ap_coder/web/static/invoice.css`)
- **D-60** · The review screen has right-click menus (`static/js/ctxmenu.js`, plain JavaScript, one component: at the pointer or under the focus with Shift+F10, inside the window, role=menu with the arrow keys, Enter and Esc, every key kept in the menu; a right-click inside a text box (Paste, the spelling: B-624), Shift + right-click and a right-click on selected text stay the browser's own). A field (a right-click on its name, its row in the Fields list or its box on the page, or Shift+F10 in its box): Clear this value, Not on this invoice, Teach where it is, Show on page, Copy value (and Add as a new vendor). A line: delete, duplicate, insert below, split, the suggested account, the GL account from the line above, clear it, put it on the lines without one (or, after a confirm, on every line). A tax line: recalculate, update from the ticked lines, delete. The page: zoom here, fit, rotate, use a word for a field, teach a field, a line from a row of words. Every change from a menu, Delete, a grid action and words used from the page can be undone: the screen is kept in the browser before it (each detail, the words taught, both grids row by row), the message offers Undo and Ctrl+Z does the same (not in a text box of another form; in a box of the review form, only while nothing was typed in it since). One change is kept, until the next one or until something is typed. "Not on this invoice" is kept in the draft only (`Draft.absent`) and only for fields an invoice may leave out (`invoice_view.ABSENT_FIELDS`: tax numbers, PO, terms, due date, bank account, invoice credited): the field stays blank with a note, the GST/HST and QST checks say once, as information, what it costs (no input tax credit or refund), "no PO quoted" goes, errors never do. The supplier template does not learn "absent": `supplier.learn` keeps where a value is printed, and teaching it a field's absence would change what every later invoice of the vendor reads, which is not small or safe. Small things with it: a double-clicked plain word fills the detail being typed in, or just left for the page (as teach mode does, with its box; never from a field's box, and a verified value or a line item's word only after asking: B-621); Enter and Shift+Enter move between the details; P opens Park and X opens Reject (open only); the invoice number has a copy button; a possible duplicate links to the other invoice (a new tab); a note is added without leaving the page; the Fields list shows an edited field as Edited; the review queue keeps its filter and scroll for the tab (sessionStorage). Why: the pilot tester asked for "delete the field" on a right-click, and the actions that took several steps (a line's account from the line above, a line between two others) are one click where the reviewer already is; Undo makes the quick ones safe to use. (`ap_coder/web/static/js/ctxmenu.js`, `ap_coder/web/static/js/invoice.js`, `ap_coder/web/invoice_view.py`, `tests/test_web_ctxmenu.py`)

## Reading and touchless approval

- **D-16** · One way to read every invoice, nothing to choose: the PDF's text or local OCR, then OvisOCR2 reads every page as a second reader; agreement makes a field verified. Why: no single reader is right on every invoice. (`ap_coder/ai/reading.py`, `.env.example`, docs/CAPTURE_DESIGN.md)
- **D-17** · Every picture becomes a PDF when it comes in; the picture is kept in `originals/` for the audit trail. Why: one format to store, show, stamp and find duplicates of. (`ap_coder/intake/pictures.py`, docs/WHATS_NEW.md)
- **D-18** · The AI reads, code does the arithmetic: tax lines are copied as printed, rates and the GL distribution are computed in Python, and GL codes are an `enum` in the schema. Why: a model must not invent amounts or accounts. (README "Design decisions", `ap_coder/core/schema.py`, `ap_coder/coding/tax.py`)
- **D-19** · Touchless processing is one company-wide switch, off by default, with one fixed bar every vendor must reach by itself, and a 5% audit sample. Why: autonomy is earned per supplier on its own invoices. (docs/CAPTURE_DESIGN.md "Touchless processing", `ap_coder/capture/supplier.py`, `ap_coder/capture/workflow.py`)
- **D-20** · Touchless gates: no approval without a person until OvisOCR2 has read it and the AI reviewer (when on) agrees with every field and line; the reviewer's and the Azure check's holds both count, whatever the order; a credit note always needs a person. Why: no person looks at a touchless invoice, and B-31, B-32 and B-42 each once let one past a gate. (docs/BUGS.md B-31, B-32, B-42, `ap_coder/ai/page_worker.py`, `ap_coder/ai/verifier.py`, `ap_coder/capture/workflow.py`)
- **D-21** · The AI reviewer never changes a value; it agrees, disagrees or is unsure, and a person decides. It runs after OvisOCR2 in the same line. Why: a person decides what is posted, and the two models never load LM Studio at once. (docs/WHATS_NEW.md "the AI reviewer", `ap_coder/ai/verifier.py`, `ap_coder/ai/page_worker.py`)
- **D-22** · Capture calibration is not refitted by bug fixes; a fix caps or lowers a confidence without changing calibration keys. Why: `calibration.json` is measured on benchmark runs (`python -m ap_coder.bench calibrate`), and a refit needs new runs. (docs/BUGS.md B-44, B-47, docs/CAPTURE_DESIGN.md, `ap_coder/capture/calibration.json`)
- **D-43** · A value read from the line just over its label (`label-above`, B-280, B-282, B-288: grids that print labels under their values) is a new evidence pattern the benchmark does not generate, so it has no measured record and keeps the reader's own score (never verified on its record alone); and on a scan or a photo an amount that no check confirms (no total read, nothing adding up with it) is likely at most, whatever its pattern's record (B-285). Why: two OCR reads share the page's geometry, so a row put on the wrong label is a mistake both make; the arithmetic is the independent witness. Neither changes the calibration keys (D-22). (`ap_coder/capture/reader.py` `labels_under_values`, `_value_over_label`; `ap_coder/capture/confidence.py` `fuse`)
- **D-44** · An invoice date or number read without a label of its own is a new evidence pattern, weaker than a labelled one and never verified on a labelled one's record: the date after the number in a title (`number-dated`: "Rechnung Nr. 471102 vom 05.03.2018", "Facture n° 562044 du 2 juillet 2015"), an invoice number alone at the far end of a header row after a real label (`label-far-right`), a value after a weak label (`weak-label-...`: "Nr.", "Numéro :", the receipt labels, which are read only when no other label for the field reads a value), and, with no label at all, a receipt's date and time (`date-time`) and a date alone beside the title (`title-dated`), which fusion holds to check however many readers see them (`UNLABELLED_CAP`); a date with no label of its own scores at most half the weakest labelled date on the page. A date that reads both ways (9/10/2020) with nothing on the page to settle it is shown month first when the first page prints a US address and nothing Canadian (no postal code, province or Canadian tax anywhere on it), still marked as reading both ways (at most 60%, check); dates printed with points (05.03.2018) are never turned month first. The calibration keys stay as they are (D-22). Why: on 135 real invoices and receipts (sweep 4) half the dates and two fifths of the invoice numbers were printed so and missed; a missing value costs a person a look, a wrong one that looks sure costs a wrong posting. (`ap_coder/capture/reader.py` `_dated_number`, `_stamped_dates`, `_title_dates`, `_far_right_header`, `_read_fields_on`; `ap_coder/capture/confidence.py` `fuse`; docs/BUGS.md B-353 to B-367)
- **D-45** · A reading found by wording the benchmark never prints (terms stated in a footer sentence, a Spanish, Italian, German or Dutch label, a PO under "Your reference", a due date in a German sentence: sweep 4, docs/BUGS.md B-373 to B-375) is marked `UNMEASURED` (`capture/types.py`): it keeps the reader's own score instead of the measured record of its reading's family ("label-inline" and the like), and is checked (0.8 at most) however many OCR reads agree, unless a measured reader reads the same value; a check on other fields (the due date = invoice date + the terms) lifts it to likely at most, never verified (B-384). Why: those records were measured on the benchmark's own wording; a new wording may fail in ways the benchmark never showed, so a person checks it until it is measured. The calibration keys stay as they are (D-22). (`ap_coder/capture/reader.py` `UNMEASURED_LABELS`, `_terms_sentences`; `ap_coder/capture/confidence.py` `fuse`)
- **D-46** · A supplier template reading is evidence of where the value was printed on the vendor's earlier invoices, so it counts as a reader only where the template can vouch for it: read by the label it was learned by (or, for a value learned with no label, such as the name at the top, at its position), at a spot *settled* by an approval where the value was printed there and nowhere else (or clicked there), or by two approvals in a row with the value there; a spot that holds another value than the one approved starts over, and a value printed twice is learned at both places so that the template's own spots disagree once they differ. Any other template reading (`UNSETTLED` in `capture/types.py`: the label not on this page, a spot not settled yet, a new label at an old spot, the template's own spots disagreeing) never decides and never counts towards verified: the value chosen is the one the other readers make strongest; it adds its agreement, or stays a rival that contests; alone it fills the field at *check*; it has its own evidence family, not measured. Learning does not follow the rule reader's choice of place (it would only repeat the reader's mistakes). The template agreeing never leaves a value less certain than the other readers alone (a floor below verified), and a rival only the template read does not contest an amount the totals add up with. Why: on the sweep 4 repeat vendors (47 later invoices) the template replaced right, labelled readings 9 times and marked 12 right values down where the layout had changed; a review with generated English supplier streams then found an agreeing, unvouched template reading made a wrong date verified and the invoice touchless (B-420 to B-422). Touchless needs every field verified, so a reading that only agrees must not be a second reader. The calibration keys stay as they are (D-22). (`ap_coder/capture/supplier.py` `learn`, `_apply_variant`, `Variant.settled`; `ap_coder/capture/confidence.py` `fuse`, `_vouched_first`, `_totals_that_add_up`; docs/BUGS.md B-387 to B-393, B-420 to B-423)
- **D-47** · What English vendor PDFs taught the reader beyond the benchmark's wording is marked `UNMEASURED` (D-45) or capped, so it starts as a person's check: a supplier's name read under a remit-to label on its own line (unless the same name is printed elsewhere on the page), a top-of-page name with nothing of a supplier's name about it (scored below `WEAK_NAME`), US dollars implied by a US supplier's "$" with nothing Canadian on the page (never printed, so *check*), the HST or GST inferred from a page that names one tax and a tax total at its rate, a business number printed without its RT program account (its check digit confirms nothing), a letter's date alone (`letter-dated`, held to check as other dates without a label); a credit known only by a line saying so in the body is likely at best. Any total on a document that takes a deposit, a prepayment or an agency's commission off before the amount to pay, and the deposit itself, are marked `TAKEN_OFF` and held to check however well they add up: whether the gross or the net is posted is AP's call, not arithmetic. A GST or HST read with no subtotal to tell its rate is likely at most (`EITHER_TAX`). Text a PDF draws sideways is read on the page turned upright and the page's `turn` set, as for a scan read turned, so the review screen shows the PDF the way it was read. Why: on 48 real English invoices (sweep 4) the dangerous readings were confident ones of patterns the benchmark never prints; a missing value costs a look, a wrong verified one a wrong posting. The calibration keys stay as they are (D-22). (`ap_coder/capture/reader.py`, `ap_coder/capture/layout.py` `_text_turn`, `ap_coder/capture/confidence.py`; docs/BUGS.md B-394 to B-418)
- **D-50** · A supplier template learns from each page once: it keeps the pages it learned from (the file's SHA-256, the newest 100) with the value of each field it learned from each, and a page approved again (reopened for correction, sent back by the second approver, or the same file imported twice) teaches only the values it has not taught before (every value of a field it taught is kept, and every value approved is still looked for on the page, B-460), or one a reviewer clicked; it does not count as another invoice. The template is not rolled back when an approval is withdrawn (a reopen or a send-back withdraws the coding memory, the lessons and the outcomes): undoing one page's place in a running record of spots is not possible, and the page's values approved again are the same evidence. Why: approved twice, one page made a spot learned unsettled "two approvals in a row" and vouched for, and the template read the invoice date as the due date on the next invoice (B-454; D-46 counts approvals in a row). (`ap_coder/capture/supplier.py` `learn`, `Template.documents`; `ap_coder/capture/workflow.py` `learn_from_approval`)

## Tax, coding and learning

- **D-23** · Place of supply is the ship-to printed on the invoice, else the province of the cost center's site, else our province from Settings, and the vendor's province only last; one rule for the tax checks and the self-assessment. Why: that is where Canadian sales tax applies, not where the vendor is. (docs/SALES_TAX.md, `ap_coder/coding/tax.py` `supply_source`, `ap_coder/coding/taxreturn.py`, docs/BUGS.md B-13)
- **D-24** · Rates are an effective-dated CSV that finance edits (a copy in the data folder wins); the covering row with the latest `effective_from` wins (a province row on a tie). Why: rates change on a date, and file order must not decide. (`ap_coder/coding/tax.py`, `data/canada_tax_rates.csv`, docs/BUGS.md B-12)
- **D-25** · Lessons are kept per situation (vendor, document kind, field or kind of line); after 3 corrections of one situation (`why_after`, Settings → Review), approving asks "why", and the reason goes to the AI with the lesson. Why: a repeated correction is a rule nobody wrote down. (`ap_coder/ai/lessons.py`)
- **D-26** · `vendor_key` rules are versioned (`VENDOR_KEY_RULES`); the store recomputes stored keys when the version changes. Why: a new rule (French legal forms) must not split one vendor's history in two. (`ap_coder/core/memory.py`, `ap_coder/core/store.py`, docs/BUGS.md B-15)

- **D-58** · How GL coding learns from AP, measured with `bench coding` and its new `--realistic` run (2% reviewer mistakes, ERP history for 4 vendors in 10, kept chat-model guesses, one account split by quantity); thresholds set on seeds 1 to 4, reported on 31 to 34 (30 × 30). Kept: (1) other vendors' lines code a line when at least two of them agree with three quarters of the evidence (each vendor's closest line), not only when none disagrees: realistic accuracy 92.2% → 93.0%, precision 96.6% → 96.7%, default unchanged; (2) a correction against 5 or more approvals in a row of the same line is suggested with the old account beside it, not filled in by any source, until AP confirms it once (a slip looks like a change of mind until then; B-603, B-606): realistic wrong accounts 292 → 219, precision 97.4%, accuracy −0.1 point (default −0.1, the first spare part after the recode); 3 approvals was tried: 199 wrong but −0.3 point of accuracy on both runs (−0.2 on tuning seeds 3 and 4, where 5 cost nothing); (3) the history check and the chat model's examples follow a correction once it is confirmed by one more decision for the new account, whatever its outcome, each line on its own (`memory.current`, B-601, B-602, B-605), not all-time votes: neutral on the benchmark (false alarms 20 → 18 default, 49 → 52 realistic, caught 139 → 140), kept because the old count warned for about 4 lines per old approval after a recode, which grows with years of ERP history. All together (after the review fixes B-602 to B-606): default 96.0% / 99.7% / 96.3% (accuracy / precision / coverage) → 95.9% / 99.7% / 96.2%, 28 wrong both, history-check false alarms 20 → 9; realistic 92.2% / 96.6% / 95.5% → 92.9% / 97.5% / 95.3%, 292 → 212 wrong, false alarms 49 → 50. Rejected: following the latest correction at once (no warning right after a recode: default false alarms 20 → 0, but realistic catches 139 → 71 and false alarms 49 → 66, since a slip is a correction too); "usual account" at 9 in 10 of 5 or more lines (no change on 31 to 34); a kept guess learned only after a second decision (realistic accuracy 92.2% → 89.2%, or 90.0% counting a changed guess as a decision, for precision 97.0% and 96.8%); a line that went back and forth between two accounts left blank (split errors 93 → 46, but accuracy 92.2% → 91.5%); a cost center per vendor and account (the benchmark does not measure cost centers). Why: a wrong account filled in is worse than a blank, but a blank costs AP a click, so only what lowered wrong accounts without losing right ones, or for a small, stated cost, was kept. - **D-31** · Every bug gets a failing test first, then the fix, and an entry in docs/BUGS.md with its lesson; a suspicion that cannot be reproduced is logged as N-NN and left. Why: a fix without a test comes back; a blind fix breaks something else. (docs/BUGS.md, `CLAUDE.md`)

- **D-39** · "Approved as coded" has one definition and one label on Insights, Learning and Activity: an approval that changed nothing the coder proposed. - **D-41** · Line items read without column headings to go by (a table read by its amount column, a receipt's list of amounts, a summary of charges) are kept only when they prove themselves: they add up to a sum printed with them, to the subtotal, or to the total less the taxes; otherwise none are returned and the invoice is coded as one line for its subtotal.
